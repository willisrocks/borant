## 1. Claude Code first run

### What the stall is

Reproduced on borant-2 with a scratch config dir (a copy of the config, not the
real file). An authenticated first run shows, in order:

1. `Let's get started.` / `Choose the text style that looks best with your
   terminal` — the theme picker.
2. `Security notes:` … `Press Enter to continue…`
3. `Accessing workspace: <cwd>` / `Quick safety check: Is this a project you
   created or one you trust?` with `❯ No, exit` and `Yes, I trust this folder`.

The trust dialog starts on **`No, exit`**, so the obvious "press Enter"
unattended launch exits, and a launch that waits on the theme screen hangs
forever. That is the reported borant-2 symptom.

### The keys

| Key | Where | Effect | Written by the flow |
|---|---|---|---|
| `hasCompletedOnboarding` | top level of `~/.claude.json` | Skips the theme picker and the security notes; the first screen is the trust dialog | `true` |
| `projects["<absolute path>"].hasTrustDialogAccepted` | same file | Skips the trust dialog for that path and every path below it | `true` |

- There is no `theme` key to seed: after the flow `theme` is absent from
  `~/.claude.json`, so the theme choice is not persisted there and the screen
  appears once per config dir. `hasCompletedOnboarding` skips it anyway.
- Nothing in `settings.json` does this: this box has no `~/.claude/settings.json`,
  and the binary knows only `hasCompletedOnboarding` and
  `hasTrustDialogAccepted` (no `trustedFolders` key).
- `-p`/`--print`, or any non-TTY stdout, also skips the trust dialog
  (`claude --help`: "The workspace trust dialog is skipped when Claude is run in
  non-interactive mode"). That helps `-p` turns, not an interactive agent.

### Does a trusted parent cover its children?

Yes. Three runs, each in a scratch tmux session, same config otherwise:

| Config (`projects`) | Working directory | First screen |
|---|---|---|
| `{}` | `/tmp/claude-facts/other/clone` | The trust dialog (control: the test is sensitive) |
| `{"…/parent": trusted}` | `…/parent/clone` | The prompt, no dialog |
| `{"…/parent": trusted, "…/parent/clone": hasTrustDialogAccepted false}` | `…/parent/clone2` | The prompt, no dialog |

After the second run, the config had gained a `projects["…/parent/clone"]`
entry with `hasTrustDialogAccepted: false` (the session's normal bookkeeping),
and the third run still prompted nothing: the coverage comes from the trusted
parent, not from the child entries. So trusting `~/.borant/work` covers every
clone below it, including ones that were already visited.

### The seed command

Run it with no Claude Code session of that user running (it rewrites the file),
keep mode 600, and keep a copy first:

```sh
cp -p ~/.claude.json ~/.claude.json.bak-$(date +%Y%m%d-%H%M%S)
tmp=$(mktemp)
jq '.hasCompletedOnboarding = true
  | .projects = ((.projects // {})
      + {"/home/chris/.borant/work": {hasTrustDialogAccepted: true, allowedTools: []}})' \
  ~/.claude.json > "$tmp"
chmod 600 "$tmp" && mv "$tmp" ~/.claude.json
jq '{hasCompletedOnboarding, projects: (.projects | keys)}' ~/.claude.json
```

The expression was tested against a copy with the account fields stripped, and
produced exactly `hasCompletedOnboarding: true` plus the one trusted parent.
Authentication is separate: the box user needs `~/.claude/.credentials.json`
(this box has it), and no token was read or printed here.

### The stray session

At research time `tmux ls` showed only Borant worker sessions
(`borant-w-events`, `borant-w-fill`, `borant-w-mirror`, `borant-w-stores`,
`borant-w-warn`); no separate session was still parked on the theme screen, so
the stall above is the reproducible form of that bug. No session that this
research did not start was stopped.

## 2. `refs/borant/test/wip` push

From the `borant` clone on borant-2:

```sh
git push origin HEAD:refs/borant/test/wip   # * [new reference] HEAD -> refs/borant/test/wip
git ls-remote origin 'refs/borant/*'        # the ref is listed at the pushed commit
git push origin :refs/borant/test/wip       # - [deleted] refs/borant/test/wip
git ls-remote origin 'refs/borant/*'        # gone
```

The credential is the box user's GitHub CLI:

```
credential.https://github.com.helper = !<nix store>/gh/bin/gh auth git-credential
gh auth status: account willisrocks, https, token gho_… (redacted here),
                scopes gist, read:org, repo, workflow
```

So a push needs the box user's `~/.config/gh/hosts.yml` (or another credential
helper) and `repo` scope; no deploy key or app token was created. The remote
already holds 15 `refs/borant/<agent>/wip` refs, so this is the mechanism the
swarm uses today. The test ref was deleted and its absence confirmed with
`git ls-remote`; no other ref was touched.

## How this was tested

- Claude Code ran only with `CLAUDE_CONFIG_DIR` pointing at a scratch directory
  under `/tmp` (mode 700) holding a copy of `.credentials.json` (mode 600);
  the real `~/.claude.json` and `~/.claude/.credentials.json` were never
  written. Each run used
  `env -i HOME=$HOME PATH=$PATH TERM=xterm-256color CLAUDE_CONFIG_DIR=<scratch> claude`
  in a tmux session named for that test (`onboard-facts`, `onboard-parent`,
  `onboard-control`, `onboard-clone2`), stopped by that name. Screens were read
  with `tmux capture-pane -pt <name>`.
- No secret value was printed: the `gh` token and the Claude credentials were
  only ever referenced as redacted. The scratch directories were deleted after
  the runs.
